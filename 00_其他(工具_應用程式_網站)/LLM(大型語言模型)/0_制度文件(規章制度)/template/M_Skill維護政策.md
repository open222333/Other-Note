## 第 2 章：安全預設值底線（所有 skill 通用）

skill 產出的任何設定範例，不得違反以下底線（違反即等同文件 F 禁令，審查一律退回）：

- 不對公網綁定內部服務（DB、快取、內部 API）——預設 localhost 或內網。
- 不關閉安全機制當作解法：`StrictHostKeyChecking no`、關防火牆、關閉服務內建保護模式一律禁止寫進 skill。
- 不在 skill 內出現任何金鑰／token／密碼明文——一律 `$ENV_VAR` 或「部署時注入」。
- <依專案填：技術棧特有的已知腐化項，如「不使用已移除的舊認證插件」>

---

## 第 3 章：新增／修改 Skill 檢查點

改任何 skill 前逐項打勾，任一不過即停：

- [ ] 這是「步驟／方法」嗎？（是 → 放 skill；若是「現狀事實」→ 改放 G）
- [ ] 有無金鑰明文？（有 → 改 `$ENV_VAR`）
- [ ] 設定範例是否過第 2 章底線？
- [ ] 是否與既有 skill 重複？（重複 → 合併，不建第二份）
- [ ] 描述（description）觸發條件是否精準？（避免誤觸／漏觸，浪費 token）
- [ ] 次要端（手機等）會用到嗎？（會 → 依文件 K 第 4 章備妥可內嵌片段）

---

## 第 4 章：審查節奏

- **事件驅動**：每次某 skill 被實際使用且發現內容過時／有誤 → 當場開更正，改完更新該 skill 開頭版本行。
- **定期**：配合文件 G 易腐清單的核對週期，一併掃 skill 是否引用了已變的外部狀態（版本、認證方式、host key 假設）。
- **安全更新（每月，掛在文件 I §4 的每月檢視同一天）**：派 S 查 <依專案填：OS 與核心服務清單> 的安全公告與 CVE，對照文件 G 的現行版本，輸出三欄清單「項目｜影響/不影響｜建議動作」。需套補丁 → 開 H 變更單（套件升級屬文件 F ⛔，不得直接執行）；本次結果記入 I 一則「例行」。
- **退役**：不再使用的 skill 直接刪除，不保留「以防萬一」的死檔（單一真相）。

---

## 維護方式

- 本政策與 A~M 同 `docs/ai-governance/`；skill 本體在其各自位置版控。
- 第 1 章待更正項完成後直接移除該列（單一真相，Git 留歷史）。
- 新發現的安全底線 → 補進第 2 章，更新版本行。
