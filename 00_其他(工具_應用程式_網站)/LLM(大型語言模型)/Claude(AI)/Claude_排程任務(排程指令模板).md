# 概念

## 排程任務的特性

- **每次執行都是全新的對話**：不記得之前聊過什麼，提示詞要能獨立看懂
- **通常無人在旁**：遇到需要確認的事沒人回答，提示詞要先寫好判斷規則
- **讀寫本機檔案要連到電腦**：電腦需開機、Claude 桌面版需開啟並連線；關機或睡眠時該次執行會失敗
- **資料夾在排程設定裡指定**：提示詞不必寫完整路徑，但要寫清楚「要讀哪些、只能寫哪個檔案」
- **權限模式**：
  - 自動核准：執行中的操作不需確認，能力最大，**提示詞的限制更重要**
  - 需要確認：遇到需核准的操作會停住，無人時該次等於失敗

## 設定項目

| 項目 | 說明 |
|---|---|
| 名稱 | 一眼看出用途，例如「檢查SCTW優化」 |
| 提示詞 | 每次執行送出的完整指示 |
| 排程 | cron 格式，可加時區：`CRON_TZ=Asia/Shanghai 54 8 * * *`；最短間隔通常為每小時 |
| 一次性 | 指定時間執行一次後自動停用 |
| 資料夾 | 允許讀寫的本機資料夾（需要電腦時） |
| 權限模式 | 自動核准 / 需要確認 |
| 通知 | 完成時推播到手機、Email（選用） |

# 撰寫原則

## 必備要素檢查表

| 要素 | 寫法範例 |
|---|---|
| **任務目標** | 檢查可優化處、重複功能、可模板化的寫法 |
| **輸出位置與格式** | 寫到專案根目錄 `待辦事項.md`，每項格式：`- [ ] [優先度] [分類] 描述（檔案路徑）— 日期` |
| **能改什麼、不能改什麼** | 除了待辦事項.md 不修改任何檔案 |
| **git 操作** | 不執行 git add / commit / push |
| **增量範圍** | 依檔案記錄的上次 commit，只檢查之後的變更 |
| **排除項目** | node_modules、dist、.git、submodule、第三方程式碼 |
| **去重與保留** | 先讀最新內容再增修；相同問題不重複新增；不刪改使用者寫的內容 |
| **已完成項目** | 標 ✅ 加日期，超過 30 天移到「已完成」區 |
| **沒有變化時** | 沒有新發現就不修改檔案 |
| **專案規範** | 建議須符合專案 CLAUDE.md |
| **回報方式** | 結束時 3–5 行摘要；有重要發現才通知 |

## 常見衝突與風險

| 狀況 | 風險 | 對策 |
|---|---|---|
| 排程執行 git commit | 連接資料夾刪除 `.lock` 需要核准，無人時會留下 lock 檔，之後的 git 指令報「File exists」；也會把使用者未完成的改動一起提交 | 提示詞寫「不執行 git 寫入操作」，由使用者檢查後自行 commit |
| 使用者同時編輯同一檔案 | 排程重寫整個檔案會蓋掉手動修改 | 先讀最新內容，只增修自己負責的項目 |
| 專案已有多份規劃文件 | 每次可能另開新文件，資訊分散 | 指定沿用哪份文件、待辦只記狀態與新發現 |
| 未提交的改動 | 把做到一半的功能列成問題 | 寫明「只檢查已 commit 的內容」或「包含未提交改動」 |
| 與 repo 規則衝突 | 例如筆記庫要求檔名加括號、新增檔案要更新索引 | 輸出放到規則排除的位置（如 `note_temp/`），或在提示詞列為例外 |
| 自動核准權限 | 沒寫限制時可能直接改程式碼 | 明確列出唯一可寫入的檔案 |
| 每天執行但專案少變動 | 白跑、重複建議越積越多 | 沒有新 commit 就不動作，或改成每週 |
| 電腦沒開 | 該次執行失敗 | 排在電腦通常開機的時段 |

## 頻率與時間選擇

| 任務類型 | 建議頻率 |
|---|---|
| 程式碼優化檢查、文件一致性 | 每週一次 |
| 筆記庫格式檢查 | 每週或每兩週 |
| 套件與安全更新 | 每週一次 |
| 多專案變更摘要 | 每個工作日下班前 / 每週五 |
| 健康檢查 | 每小時（最短間隔） |
| 技術資訊追蹤 | 每週一次 |

- 時間避開整點與半點（例如 08:54 而非 09:00），整點排程多、可能延遲
- 一個專案一個排程，不要寫「檢查全部專案」，範圍太大結果不穩定

## 共用規則區塊

附加在各模板最後，依需要刪減：

```
規則：
- 只檢查與記錄：除了 <輸出檔案>，不修改任何檔案
- 不執行 git add / commit / push，不安裝套件，不執行會修改檔案的指令
- 排除：node_modules、dist、build、.git、submodule、第三方程式碼
- 先讀取 <輸出檔案> 的最新內容再增修；相同問題不重複新增；不刪改使用者自己寫的內容
- 沒有新發現就不修改檔案
- 建議須符合專案 CLAUDE.md 的規範
- 結束時用 3–5 行摘要：新增幾項、完成幾項、最重要的一項
```

## 1. 程式碼優化檢查（記錄到待辦）

- 需要電腦：是（連接專案資料夾）
- 建議頻率：每週

```
檢查專案中：
1. 可優化處：效能、資源使用（查詢、快取、打包大小）、UI/UX、可維護性
2. 重複功能：重複或幾乎相同的程式碼、元件、設定
3. 可模板化 / 規範化的相似寫法；跨專案通用的模式標註「可抽成 Template」
記錄或更新到專案根目錄的 待辦事項.md。

待辦事項.md 格式：
- 開頭記錄「檢查日期」與「對應 commit」
- 依 <docs/優化方案.md> 的章節代號記錄狀態（⬜ 未開始 / 🟡 部分完成 / ✅ 完成），新發現另列一節
- 每項：編號、項目、位置（檔案 / 函式）、問題、建議做法、優先度

範圍：
- 依開頭記錄的 commit，只檢查之後已 commit 的變更；第一次執行則全專案檢查
- 不含未提交的改動；沒有新 commit 就不修改檔案
- ✅ 超過 30 天的項目移到檔案最下方「已完成」區

<共用規則區塊>
```

## 2. 筆記庫格式檢查

- 需要電腦：是（連接筆記庫資料夾）
- 建議頻率：每週或每兩週
- 輸出放到規則排除的暫存區，避免違反筆記命名與索引規則

```
依 CLAUDE.md 與 00_sample/00_筆記規範.md 檢查筆記庫：
1. README.md 筆記索引的連結是否都存在
2. 筆記內相對連結是否失效
3. 目錄錨點是否對得上標題
4. 是否缺少開頭摘要、目錄、參考資料
5. 範本殘留的空章節（sample、Debian / Ubuntu 等只有空 code block）
6. 是否有金鑰、token、密碼明文

結果寫到 note_temp/筆記檢查報告.md（覆寫），每項列出檔案路徑、行號、問題、建議修正。
不修改任何筆記；submodule 與 *_Code 目錄只讀不檢查。

<共用規則區塊>
```

## 3. 套件與安全更新檢查

- 需要電腦：是（需讀 lock 檔；若 repo 在 GitHub 也可改用雲端）
- 建議頻率：每週

```
檢查專案的相依套件：
1. 前端：讀 package.json / package-lock.json，列出有新版本的套件（區分 patch / minor / major）
2. 後端：讀 requirements*.txt，列出有新版本的套件
3. 已知安全漏洞（npm audit、pip-audit 或查詢公開 CVE 資料）
4. major 版本升級需注意的破壞性變更（附官方 changelog 連結）

結果記錄到 <待辦事項.md> 的「套件更新」一節：套件、目前版本、最新版本、類型、是否有安全問題、建議。
只記錄不升級；不執行 npm install / pip install。

<共用規則區塊>
```

## 4. 多專案變更摘要

- 需要電腦：是（連接 repo 上層資料夾）
- 建議頻率：工作日下班前或每週五

```
彙整以下專案在 <過去 1 天 / 過去 7 天> 的變更：
<專案A>、<專案B>、<專案C>

每個專案列出：
- commit 數與主要變更（依 commit 訊息歸納成 3 行內）
- 未提交的改動（檔案數、主要檔案）
- 未 push 的 commit 數

全部沒有變更時只回覆「無變更」。只讀取 git 狀態，不執行任何 git 寫入操作。
```

## 5. 網站 / 服務健康檢查

- 需要電腦：否（公開網址可在雲端檢查；內網服務才需要電腦）
- 建議頻率：每小時
- 搭配推播通知，只在異常時通知

```
檢查以下網址：
- <https://example.com>（預期 200，回應時間 < 2 秒）
- <https://example.com/api/v1/health>（預期 200，回應 JSON 的 status 為 ok）

全部正常：只回覆「正常」，不要其他內容。
有異常：列出網址、狀態碼或錯誤、回應時間，並標題寫「⚠️ 服務異常」。
只發送 GET 請求，不登入、不送出表單。
```

## 6. 文件與程式碼一致性檢查

- 需要電腦：是
- 建議頻率：每週

```
比對專案文件與實際程式碼是否一致：
1. README.md 的安裝步驟、指令、環境變數是否與實際檔案相符（.env.default、package.json scripts、docker-compose）
2. API 文件與實際路由是否一致（多出 / 缺少的端點）
3. CLAUDE.md 規範與現有程式碼的明顯違反處

結果記錄到 <待辦事項.md> 的「文件同步」一節：文件位置、與程式碼不符之處、建議以哪一方為準。
只記錄不修改文件。

<共用規則區塊>
```

## 7. 技術資訊追蹤（不需電腦）

- 需要電腦：否
- 建議頻率：每週

```
搜尋過去 7 天以下技術的重要消息：
<React、Vite、Tailwind CSS、FastAPI、PostgreSQL / pgvector>

只列出：新的 major / minor 版本、破壞性變更、安全公告、官方停止支援公告。
每項一行：技術、消息、日期、官方連結。沒有重要消息就回覆「本週無重要更新」。
只引用官方網站、官方 GitHub release 或官方部落格。
```

## 8. 一次性提醒

- 用「指定時間執行一次」，或在對話中請 Claude 稍後提醒（回到同一個對話）

```
提醒我：<事項>。
到時檢查 <檔案 / PR / 網址> 的目前狀態，並用一句話說明是否已完成。
```

# 實例：檢查SCTW優化

- 專案：`Other-StarCitizenToolWeb`
- 排程：`CRON_TZ=Asia/Shanghai 54 8 * * *`（每天 08:54），權限：自動核准
- 原始提示詞：

```
檢查是否有可以優化地方
檢查是否有重複功能
檢查是否有相似功能可以模板化規範化
並記錄或更新到待辦事項.md
```

- 首次執行結果：產生的待辦事項.md 自行加上檢查日期、對應 commit、狀態圖示，並沿用 docs/ 既有方案章節代號；但這些都不是提示詞要求的，下次不一定照做
- 建議補上的規則：

```
規則：
- 只檢查與記錄：除了待辦事項.md，不修改任何檔案；不執行 git add / commit / push
- 計畫與章節代號沿用 docs/現版本優化方案.md、docs/專案優化建議.md；待辦事項.md 只記「目前狀態」與「新發現」，不另開新文件
- 依待辦事項.md 開頭記錄的 commit，只檢查之後已 commit 的變更（不含未提交的改動）；沒有新 commit 就不修改檔案
- 先讀最新的待辦事項.md 再增修；相同問題不重複新增，不刪改使用者自己寫的內容
- 已完成的項目標 ✅ 並註明日期；✅ 超過 30 天的移到檔案最下方「已完成」區
- 建議須符合專案 CLAUDE.md 的規範
- 更新檔案開頭的檢查日期與對應 commit
```

# 建立與修改排程

- 在 Claude 對話中直接描述：「建立排程，每週一 08:54 執行以下提示詞，資料夾 <路徑>」
- 修改名稱、時間、啟用狀態可直接改；**綁定電腦的排程修改提示詞時，需在連到同一台電腦的桌面版核准**
- 停用而非刪除：刪除會一併刪掉執行紀錄
- 第一次建立後手動觸發一次，確認輸出格式符合預期再放著自動跑
