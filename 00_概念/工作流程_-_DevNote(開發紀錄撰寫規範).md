# 工作流程 - DevNote(開發紀錄撰寫規範)

```
dev_note 是每個專案底下的「開發紀錄」目錄：每一次 bug 追查、功能修改、資料修正都留一份完整紀錄，
寫清楚問題怎麼發現、根因是什麼、證據在哪、怎麼修、怎麼驗。
目的：三個月後有人問「這個當初為什麼這樣改」，看這一份就夠，不用回去翻聊天紀錄與 commit log。
```

# 什麼時候要寫

| 情況 | 要寫嗎 |
|------|--------|
| 線上／測試站回報的異常，且已定位到程式或設定 | **要** |
| 新增或變更對外行為（API、參數、平台差異、爬蟲行為） | **要** |
| 資料同步、排程、快取行為的修正 | **要** |
| 追了一輪最後證明「不是 bug」 | **要**（結論寫「已排除」，避免下次重追） |
| 純 typo、純格式調整、只動註解 | 不用 |
| 本機環境設定問題（非程式碼） | 併入該案例的「測試步驟與環境設置」那一份，不另開目錄 |
| 純現況調查、規則尚未定案 | 寫進專案的輕量調查目錄（如 `test_note/`），等真的動程式碼再視情況搬進 dev_note |

```
原則：只要花超過半小時追查，就值得留一份。
決定要寫之後先挑分類再動筆——fix 的重點是根因與證據，feat 的重點是設計取捨與相容性。
同一件事不要在 dev_note 與其他紀錄目錄各寫一份。
```

# 分類

每一篇 dev_note **開頭都要標分類**。分類決定別人搜目錄時怎麼找到這篇，寧可標得保守，也不要不標。

## 主分類

必填、只能選一個。代號沿用 commit type，寫紀錄跟寫 commit 用同一套詞彙。

| 代號 | 分類 | 什麼情況用 | 對應 commit |
|------|------|-----------|-------------|
| `fix` | 修正 bug | 既有行為壞掉或不符預期 | `fix(...)` |
| `feat` | 新增功能 | 原本就沒有的東西：新 API、新參數、新爬蟲、新排程 | `feat(...)` |
| `perf` | 效能問題 | 行為是對的，但慢、吃資源、拖垮其他服務 | `perf(...)` |
| `data` | 資料修正／同步 | 程式沒問題，是資料髒掉、沒同步、欄位沒補；含一次性補資料腳本 | `fix(...)` 或無 |
| `ops` | 環境／部署／設定 | docker、env、nginx、排程開關、CDN 設定，不動程式碼 | `chore(...)` 或無 |
| `refactor` | 重構 | 行為完全不變的結構調整；改動大、風險高才寫 | `refactor(...)` |
| `security` | 安全性 | 權限、簽章、金鑰、越權、資料外洩 | `fix(...)` |
| `investigate` | 追查後排除 | 追完證明不是 bug、或不在我方。**一定要留** | 無 |
| `guide` | 操作指南 | 沒有程式改動，純流程／環境紀錄 | 無 |

## 跨多類時怎麼選主分類

1. 先問「**使用者／回報者感受到的是什麼**」——覺得壞了是 `fix`，覺得多了東西是 `feat`。
2. 追 bug 時順手加了功能 → 主分類仍是 `fix`，功能寫進副分類。
3. 為了新功能才踩出來的 bug（功能還沒上線過）→ `feat`。
4. 查了半天發現是資料沒同步 → `data`，不是 `fix`（程式沒改）。
5. 查了半天發現是本機 env 沒設 → `ops`，通常不單獨開目錄，併進該案例的「測試步驟與環境設置」。

## 副分類

選填、可多個，用同一組代號。主分類蓋不住的部分放這裡。

```
分類：fix（副：data, ops）    ← 追 bug 時一併補了診斷腳本、又改了 compose
```

## 嚴重度

`fix` / `perf` / `security` 必填，其餘選填（`guide` 寫「—」）。

| 代號 | 判準 | 期望處理速度 |
|------|------|-------------|
| `P0` | 線上全面不可用、金流／扣點算錯、資料大量污染、資安外洩 | 立刻，可直接 hotfix |
| `P1` | 主要功能異常但有 workaround，或只影響部分使用者 | 當天內 |
| `P2` | 次要功能、特定平台或特定條件才會踩到 | 排進本輪 |
| `P3` | 體感問題、文件、技術債 | 有空再做 |

- 判斷看**影響面 × 有無替代路徑**，不看「修起來難不難」。
- 專案可加規則：例如跟會員權益直接相關的算錯（看片次數、VIP、扣點）一律至少 `P1`。

## 影響範圍

必填，寫得越具體越好。三個面向各挑一個以上，用頓號串起來；可選值由各專案定義：

| 面向 | 說明 | 例 |
|------|------|-----|
| 環境 | 正式站 / 測試站 / 本機 | 正式站 |
| 平台或對象 | 全平台 / iOS / Android / Web / PWA，或爬蟲名稱 | iOS |
| 端點或元件 | API 版本、後台、worker、排程、快取、搜尋、CDN、DB、S3… | v3 搜尋端點 |

```
例：正式站、iOS、v3 搜尋端點
    正式站、全平台、s1 + sw2 影片 m3u8 端點
    測試站、laosijiA_crawler、crawl task
```

同一功能有多份實作（例如兩個 Blueprint）的專案，端點欄**一定要寫清楚是哪一份或兩者皆是**。

## 標記位置

兩個地方都要，不要只寫一邊：

1. **主紀錄 md 的 H1 底下**，用引言區塊（見「主紀錄章節骨架」）
2. **`dev_note/README.md` 的案例索引表格**，`分類` 與 `嚴重度` 兩欄

```
分類不進目錄名：分類可能在追查途中改變（常見 fix → data），
改目錄名會連帶動到 README、容器掛載路徑與所有交叉連結，代價太大。
```

# 目錄與命名

```
dev_note/
├── CLAUDE.md                       ← 專案的撰寫規範（引用本篇＋專案專屬內容）
├── README.md                       ← 目錄區塊＋案例索引表格
├── test_config.ini                 ← 所有驗證腳本共用設定（需要時）
└── YYYYMMDD_{英文_slug}/           ← 一個案例一個目錄
    ├── YYYYMMDD_{中文標題}.md      ← 主紀錄（必要）
    ├── YYYYMMDD_{中文標題}.md      ← 同案例的後續文件（選用）
    ├── GUIDE.md / README.md        ← 導讀或快速索引（選用）
    └── test_*.py                   ← 驗證腳本（選用）
```

1. **目錄名** = `YYYYMMDD_` + 全小寫英文 slug，用底線不用連字號。日期取「問題被提出／開始追查」那天，不是修完那天。
   例：`20260826_deepmosaics_sync_hthd_183`
2. **檔名** = `YYYYMMDD_` + 中文標題，字詞間用底線。日期取「這份文件寫的那天」，同目錄可有多個不同日期的 md。
   例：`20260902_看片次數重複扣點與顯示未歸零.md`
3. **一個案例可拆多份 md**：
   - `YYYYMMDD_{現象}.md` —— 追查與修復本體
   - `YYYYMMDD_{主題}_測試步驟與環境設置.md` —— 怎麼測、環境長什麼樣、踩到的環境坑
   - 拆的判準：主文超過約 600 行，或「怎麼測」的篇幅蓋過「為什麼這樣改」。
4. slug 用**現象或功能**命名，不用票號當唯一識別（票號放標題裡）。
5. dev_note 有掛進容器時（例如 `./dev_note:/opt/dev_note:ro`），改目錄名要一起搜
   `docker-compose.yml`、專案 README / CLAUDE.md 裡的硬編路徑。

## dev_note/README.md

- **最上方**（撰寫規範提示之後、案例索引表格之前）放 `## 目錄`，用錨點列出 README 本身各章節（含巢狀子章節）。
- 新增或改名章節時同步更新目錄；錨點用 GitHub slugify：全小寫、空白換 `-`、標點直接刪除不補 `-`，底線與英數字保留。
- 案例目錄建好後，**同步在案例索引表格加一列**，`分類` / `嚴重度` 與主紀錄一致。

```markdown
## 目錄

- [案例索引](#案例索引)
- [共用設定](#共用設定)
- [執行方式](#執行方式)
  - [s1 / sw2 都要測](#s1--sw2-都要測)

## 案例索引

| 日期 | 目錄 | 標題 | 分類 | 嚴重度 |
|------|------|------|------|--------|
| 2026-09-02 | [20260902_video_click_count](20260902_video_click_count/) | 看片次數重複扣點 | `fix` | `P1` |
```

# 寫作規則

**證據優先**

- 每個結論後面要有可重跑的東西：SQL、mongo query、`redis-cli`、`grep`、`docker logs` 片段、task 名稱。
- 貼查詢就要貼查出來的數字。「大量重複」不算，「14 分鐘內同一支影片 96 筆」才算。
- 推測與事實分開，推測寫「推測」。
- 現象有多種成因形狀時，**分開統計、分開下結論**。

**程式碼引用**

- 一律 `path/to/file.py:619-620` 的 `檔案:行號` 格式。
- 貼原樣，不順手美化；修復後的版本另外貼一段對照。
- 行號會漂移，旁邊一定要有足夠的程式碼片段讓人搜得到。

**狀態表格化**

- 多成因、多 commit、多方案一律用表格，不寫成一長段。
- commit 附**完整 40 碼 SHA**（短 SHA 會撞），另附時間與訊息。
- 還沒 commit 的修改寫「（待補）」並附預計的 commit 訊息，commit 後回頭補 SHA。

**不要寫成流水帳**

- 記的是「結論與依據」，不是「第一步做了什麼、第二步做了什麼」。
- 走錯的路只在「方案比較」或「教訓」留一行。

**語言**

- 全篇繁體中文；程式碼、變數名、路徑保留原文。
- 標題寫現象，不寫「XX 問題修復」這種沒資訊量的字。

**容器內指令兩種寫法都附**

要在容器內跑的指令（排程手動觸發、`python -c` 診斷、查資料），一律同時附：

```bash
# 1. 容器外直接下（複製貼上就能跑，適合單次診斷、貼進文件）
docker compose exec -T <service> python -c "..."

# 2. 進容器後再執行（適合連續下多個指令、要用容器內 shell / 工具鏈）
docker compose exec -ti <service> bash
python -c "..."
```

只示範一種，下次照抄時另一種情境容易漏掉。

# 脫敏規則

dev_note 會進 git，寫之前先確認：

| 內容 | 處理 |
|------|------|
| 密碼、API key、AES key/IV、JWT secret、DB 密碼、S3 key、NAS 認證 | ❌ 一律寫 `<REDACTED>` |
| 完整可用 token | ❌ 截斷或寫 `<token>` |
| 環境變數的**變數名與結構** | ✅ 可以寫（幫助重現），值要脫敏 |
| 測試站 host、port、容器名 | ✅ 可以寫 |
| 帳號 / member_id、內容名稱 | ⚠️ 只在追查必要時出現，不附帶其他個資 |

# 驗證腳本規範

- 放在案例目錄，命名 `test_*.py`。
- 共用設定讀 `../test_config.ini`，**不硬編 URL / 平台 / 番號 / 爬蟲名稱**：

```python
import configparser
import os

_cfg = configparser.ConfigParser()
_cfg.read(os.path.join(os.path.dirname(__file__), "..", "test_config.ini"))

BASE_URL = _cfg.get("api", "base_url", fallback="http://localhost:20080/v3")
```

- 預設不依賴容器內環境，直接在本機打 HTTP；
  例外（要 import 專案程式、或需要只有容器內才有的 env）在 md 寫清楚用 `docker compose exec` 執行，
  並自行補 `sys.path`。
- **必須包含迴歸檢查**（舊行為不變），不能只驗新功能。
- 每項檢查用 `check(name, ok, detail)` 累計，結尾用 exit code 表示：`0` 全過 / `1` 有失敗 / `2` 設定錯誤。
- 全部 PASS 才算過；SKIP 要在 md 寫明原因。
- 現有測試沒覆蓋的新函式，直接對真正的 DB / 快取驗證，md 放「修復前 vs 修復後」對照。
- 沒有現成 runner 時，md 寫明手動驗證方式（觸發哪個 task、查哪個 collection 的哪些欄位）。

# 標準流程

改完程式後依序做完，**文件與程式修改同一批交付**，不另外補。

| 階段 | 做什麼 | 重點 |
|------|--------|------|
| 1. 靜態檢查 | `python3 -m py_compile <改動的 .py>` | import 補齊；新函式有在 `__init__.py` export；新排程 / task 有掛上 |
| 2. 多份實作同步檢查 | `grep -n "<函式或路由名>" <各份實作>` | 只在同功能有多份程式碼的專案；複製貼上要逐行確認差異，紀錄寫明兩邊都改或為何只改一邊 |
| 3. 容器起得來 | `docker compose up -d && docker compose ps`、`docker logs --tail 50 <容器>` | 全部 Up、無 traceback |
| 4. 自動化測試 | 專案單元測試 + `python dev_note/{案例}/test_*.py` | 含迴歸項 |
| 5. 手動驗證 | Postman 集合 / 觸發 task / 查 DB | 順序：取 token → 取資源 → 新功能 → 迴歸 → 邊界（無資料 / 未設定） |
| 6. 更新文件 | 見下表 | 每次都要 |

```
環境陷阱：
- 改了 env_file 要 docker compose up -d --force-recreate <service>，docker restart 不會重讀 env_file
- 本機用 Postman 測 localhost 前，先關掉 Postman 的 System Proxy，否則會被代理攔截
```
